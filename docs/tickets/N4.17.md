# N4.17 — Implement bounded search monitoring

## Ticket

- **Stage:** 4 — Search vertical slice remediation.
- **One question:** Can search availability, latency, execution failures, quota rejections, mock payment challenges, and mock-paid completions be observed through a strict low-cardinality internal boundary without changing customer responses or claiming delivered staging telemetry?
- **Inputs allowed:** existing N3.1 metric/alert contracts, search HTTP lifecycle, deterministic repository-local aggregation, an optional injected exporter, strict schemas, and loopback tests. No external collector, dashboard, paging service, cloud/IAM mutation, payment, or USDC spend.
- **Freshness date:** 2026-07-31.
- **Secrets involved:** none.

## Decision

Add an internal search monitor that accepts only fixed product and outcome values, emits existing allowlisted metric points, creates a fixed safe alert for bounded execution failures, retains bounded immutable snapshots, and contains optional exporter failures. Wire it into the search HTTP server without adding a public endpoint or response field.

## Validation contract

- **Focused test:** `npm run test:n4.17`.
- **Failure test:** dynamic products/outcomes, negative duration, unbounded retained points, mutable snapshots, unsafe cardinality, exporter failure, and monitor exceptions fail closed or remain isolated from customer behavior.
- **Acceptance:** canonical repository acceptance, schema/discovery generation, Stage 4 recomputation, staging loopback smoke, boundary verification, secret scan, and diff checks.
- **Cost/network effects:** loopback HTTP only, no external traffic, and 0 USDC spent.

## Completion

- **Result:** bounded search monitoring is repository-verified for internal snapshots and loopback HTTP lifecycle signals; collector delivery, dashboards, paging, and staging monitoring remain unverified.
- **Focused validation:** `npm run test:n4.17` passed 6/6.
- **Stage effect:** `monitoring` advances from `missing` to `repository_verified`, but remains `stagingVerified=false`; Stage 4 remains blocked.
