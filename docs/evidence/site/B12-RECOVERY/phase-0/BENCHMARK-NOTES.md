# B12 recovery — current functional benchmark notes

Observed 2026-08-11. These are official primary-source product surfaces and are
functional references only. Clervo must not copy their visual identity, claims,
metrics, or unsupported product states.

## Home / marketing narrative — Linear and Vercel

Sources: <https://linear.app/> and <https://vercel.com/>.

- **What the market leader does well:** Linear couples each narrative chapter
  to recognizable product UI and an explicit workflow; Vercel connects product
  families to concrete deployment/agent mechanisms and specific next actions.
- **What Clervo should adopt functionally:** first-fold category/promise/action;
  progressive explanation using the actual request-to-receipt mechanism; one
  useful interaction that teaches product behavior.
- **What Clervo should not copy:** Linear's product-management grammar,
  Vercel's deployment vocabulary, customer metrics, logo walls, or visual
  compositions.
- **What Clervo can do better:** make cost, qualification, evidence, receipt,
  and replay visible in the same bounded task story.

## Product platform — Stripe and Vercel

Sources: <https://stripe.com/> and <https://vercel.com/>.

- **What the market leader does well:** Stripe explains a broad platform as
  products that work separately or together; Vercel distinguishes stack,
  platform, and tools in navigation and narrative.
- **What Clervo should adopt functionally:** explain why the operating layer
  exists, show the connected family model, and preserve direct access to each
  family.
- **What Clervo should not copy:** broad enterprise claims, business metrics,
  generalized mega-navigation, or unrelated platform categories.
- **What Clervo can do better:** show the exact transition from intent through
  qualification, cost/policy, execution, verification, evidence, receipt, and
  replay.

## Models — OpenRouter

Sources: <https://openrouter.ai/models/> and
<https://openrouter.ai/docs/guides/overview/models>.

- **What the market leader does well:** immediate search; list/table views;
  modality, price, context, supported-parameter, policy, and routing filters;
  server/API parity; single-model lookup; aliases resolve to canonical models.
- **What Clervo should adopt functionally:** dense browse-first composition,
  backed filters, technical view, creator hierarchy, exact copyable ID, and
  explicit alias/canonical distinction.
- **What Clervo should not copy:** token-popularity metrics, rankings,
  throughput/latency claims, provider counts, or creator/provider terminology
  unsupported by Clervo authority.
- **What Clervo can do better:** keep creator separate from execution supplier,
  show current Clervo lifecycle/proof/quote behavior, and link each modality to
  its executable operation contract.

## Docs — Stripe Docs, GitBook, and Vercel Docs

Sources: <https://docs.stripe.com/>, <https://gitbook.com/docs>, and
<https://vercel.com/docs>.

- **What the market leader does well:** Stripe separates task guides,
  quickstarts, product docs, and API reference while exposing terminal/agent
  access; GitBook provides persistent hierarchy, page outline, prev/next, and
  Cmd/Ctrl-K search across pages and sections; Vercel provides a clear
  get-started layer and quick references.
- **What Clervo should adopt functionally:** docs-specific shell, persistent
  grouped navigation, local static search, article TOC, copyable code,
  prev/next, deep links, and explicit current package versions.
- **What Clervo should not copy:** external AI-search dependence, account-
  personalized data, excessive nesting, or the leaders' visual chrome.
- **What Clervo can do better:** search one index across concepts, errors,
  operations, and models; keep the same operation visible across Router, MCP,
  TypeScript, Python, raw HTTP, and OpenAI-compatible interfaces.

## Start / quickstart — Stripe Quickstarts

Source: <https://docs.stripe.com/quickstarts>.

- **What the market leader does well:** goal-based quickstart selection,
  end-to-end examples, language/framework variants, stepwise implementation,
  and an isolated no-account sandbox path where supported.
- **What Clervo should adopt functionally:** choose integration first; install;
  verify; run a real free result; defer wallet concepts; expose paid-use,
  receipt, replay, reconcile, and doctor only when relevant.
- **What Clervo should not copy:** payment-domain onboarding, account setup,
  hosted IDE integration, or any sandbox capability Clervo has not shipped.
- **What Clervo can do better:** converge five interfaces on the same local
  Clervo Connect state and show one no-charge replay/recovery contract.

## Operation reference — Stripe API Reference

Source: <https://docs.stripe.com/api?lang=curl>.

- **What the market leader does well:** exact base URL, resource-oriented
  contract, standard HTTP behavior, selectable official clients, sandbox/live
  boundary, version context, and deep-linkable resources.
- **What Clervo should adopt functionally:** operation-local navigation,
  request/result schemas, required/optional fields, client switching, copy,
  errors, HTTP behavior, lifecycle, quote/payment, receipt, replay, and limits.
- **What Clervo should not copy:** Stripe resources, authentication model,
  two-column density where it harms mobile, or account-specific examples.
- **What Clervo can do better:** keep qualification, maximum charge, evidence,
  provenance, settlement uncertainty, reconciliation, and no-charge replay in
  the executable contract.

## Status — OpenAI Status

Source: <https://status.openai.com/>.

- **What the market leader does well:** current state is the first message;
  systems are grouped; history is a separate action; aggregate metrics carry an
  explicit scope caveat.
- **What Clervo should adopt functionally:** current observation time, family
  state, affected model/route drill-down, reason, and a separate history
  concept only when authority exists.
- **What Clervo should not copy:** “fully operational,” uptime percentages,
  incident history, or aggregation Clervo cannot prove.
- **What Clervo can do better:** keep lifecycle and proof level distinct and
  connect each affected state to product, model, operation, and evidence.

## Pricing — OpenRouter Pricing

Source: <https://openrouter.ai/pricing>.

- **Browser-observed functional behavior:** the page places plan-mode controls
  and one dense comparison table before an extensive disclosure-based FAQ. The
  table makes fees, model/provider coverage, budgets/spend controls, payment
  methods, limits, and model-based pricing comparable; the FAQ explicitly
  exposes billing, failed/fallback attempts, limits, pricing changes, privacy,
  and provider/model failure questions. The 390px observation retained the
  comparison and disclosure controls without document overflow.
- **What Clervo should adopt functionally:** compact comparability; direct
  answers for dynamic/model-dependent price, limits, refusal/failure, replay,
  and settlement; links from pricing rows into the matching product/operation.
- **What Clervo should not copy:** Free/Pay-as-you-go/Enterprise subscription
  structure, platform fees, provider/model counts, business model, or visual
  identity.
- **What Clervo can do better:** explain the real Clervo sequence—free first,
  per-operation economics, quote before action, maximum authorization/spend
  boundary, fixed or model-dependent pricing, failure, replay, and settlement—
  without forcing a user to infer it from plan tiers.

## Trust / security — Cloudflare Trust Hub

Source: <https://www.cloudflare.com/trust-hub/>.

- **What the market leader does well:** subject-based taxonomy for privacy,
  data protection, responsible AI, compliance, technologies, trust and safety,
  policies, and external evidence.
- **What Clervo should adopt functionally:** structured subjects, direct policy
  links, explicit mechanism/evidence state, and separation of product security
  from legal/privacy material.
- **What Clervo should not copy:** certifications, customer logos, enterprise
  scope, network claims, or third-party assurance Clervo does not hold.
- **What Clervo can do better:** explain local custody, secret handling, spend
  refusal, idempotency, settlement uncertainty, supplier boundaries, proof
  boundaries, and exact unclaimed assurance.

## Changelog — Linear

Source: <https://linear.app/changelog>.

- **What the market leader does well:** dated feed first, search/category
  navigation, grouped fixes and improvements, direct docs links, and concise
  impact explanations.
- **What Clervo should adopt functionally:** date, release/product, concise
  change, why it matters, and related docs/product links with source stated.
- **What Clervo should not copy:** media-heavy editorial treatment, release
  volume, categories, or product breadth Clervo does not have.
- **What Clervo can do better:** bind public entries to repository/release
  truth and distinguish a release event from a current operational observation.

## Proof — intentionally Clervo-specific

No market surface is adopted as a proof-page template. Clervo's opportunity is
the inspectable relationship among operation identity, result identity,
evidence, provenance, receipt, settlement, replay, reconciliation, and proof
level. The functional benchmark is the actual Clervo receipt/evidence contract,
not a competitor dashboard.

and overflow results are in `benchmark-browser-observations.json`. This is a
functional bar, not a visual source.
