# N4.15 Search Language and Region Options

## Decision

Every normalized search request carries explicit `language` and `region` values. Omitted values default deterministically to `en` and `US`. Language values must already be canonical BCP 47 tags accepted by the pinned JavaScript runtime; region values must be recognized uppercase two-letter region codes. Malformed, non-canonical, unknown, and Unicode pseudo-region values fail closed rather than being silently rewritten.

The normalized values participate in the canonical HTTP request hash and search-cache request hash. They propagate into both retrieval execution paths, the federation report, the assembly report, and the public `SearchResponse`. Executor output verification rejects any response whose locale differs from the normalized request before HTTP output or receipt construction.

## Scope and provider semantics

This ticket defines and proves a provider-neutral contract. It does not claim that Brave Search, Common Crawl, a browser, or any other live supplier accepts or honors the options. A future live adapter must map the canonical values explicitly, document unsupported combinations, and prove behavior in staging without weakening the core request/response binding.

## Rejected alternatives

- Silently lowercase or otherwise canonicalize user input: rejected because multiple byte representations would obscure request identity and caller mistakes.
- Infer region from language: rejected because language and regional preference are independent controls.
- Keep locale only at the HTTP edge: rejected because cache reuse, federation, assembly, and returned evidence could then cross locale boundaries.
- Add provider-specific parameter names to the public contract: rejected because provider qualification and adapter mapping remain separate responsibilities.
