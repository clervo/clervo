# N4.27T isolated cloud qualification design

**Decision date:** 2026-08-01

## Decision

Use one disposable zonal GKE Standard cluster with one `e2-standard-2` node and
one digest-pinned qualification image. The image runs the ten frozen developer
registry tasks and all twenty frozen browser fixtures inside one Kubernetes Job
with `backoffLimit: 0`. It exposes no public ingress and uses a process-local,
TLS-SPKI-pinned fixture boundary for deterministic JavaScript and hostile-page
content. No separate fixture VM, load balancer or search deployment exists, so
the prior overlapping-resource failure class cannot recur.

The developer path calls only the public npm Registry and GitHub repository
metadata APIs. The browser path uses Chromium in the same nonroot, read-only,
bounded process model prepared locally. Hostile output remains hash-only
`untrusted_evidence_only` and cannot affect routing, tools, policy, payment or
the evaluator.

## Authority and cost

The owner granted the configured deployer access and ordered execution after
receiving the exact plan. Only `bloxsniper-prod/us-central1/us-central1-a` and
`clervo-n427t-*` resources are permitted. The gross and daily ceilings are USD
5, maximum lifetime is six hours, validation execution count is one, third-
party API cash cost is zero, residual exposure must be USD 0/day, and IAM,
billing, production, legacy, public-ingress, payment and later-ticket actions
remain forbidden.

The execution environment refuses billing-account inspection. The evidence
therefore records the owner's stated USD 1,700 startup-credit balance as
unverified and applies the separately owner-authorized USD 5 gross attached-
billing ceiling regardless of how Google allocates the charge.

## Freeze and failure handling

The generic evaluator is tested only with synthetic material. Before the image
is built, hash the original validation corpus/labels, evaluator, worker, runtime,
adapter, Dockerfile, Job and cloud plan and commit them. After the image digest
is known, bind it in a second pre-run execution manifest. The final job may be
created once. Any pass, degradation, failure, timeout or unknown outcome is
preserved without rerun or tuning. Cleanup is synchronous and followed by
fresh negative inventory for exact prefixes, labels and pending operations.
