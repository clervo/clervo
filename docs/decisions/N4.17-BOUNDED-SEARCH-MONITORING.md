# N4.17 Bounded Search Monitoring

## Decision

Search monitoring is an internal dependency rather than a customer response field or public endpoint. The search server records only fixed lifecycle outcomes for the exact `search.web` and `search.answer` products: successful execution, failed execution, free-quota rejection, mock payment challenge, and mock-paid completion. Successful and failed executions contribute to availability; timed lifecycle outcomes contribute to latency.

The monitor reuses the N3.1 allowlisted metric and alert contracts. Snapshots retain at most 128 metric points and 32 alerts, omit request hashes and operation identifiers from metric dimensions, are deeply immutable, and have a strict schema. Execution failures create only the fixed `search.execution_failure` alert summary.

## Export boundary

An optional injected exporter may receive a snapshot. Exporter exceptions are contained and counted; they never alter customer search responses. No vendor SDK, collector URL, credential, public monitoring route, dashboard, paging integration, or automatic network delivery is selected in this ticket.

## Scope and claims

Repository-local loopback tests prove signal recording, aggregation, schema bounds, safe alerting, and failure isolation. They do not prove telemetry delivery, alert receipt, dashboards, SLOs, staging availability, load behavior, or any external monitoring system.

## Rejected alternatives

- Add monitoring fields to search responses: rejected because internal operational state is not part of the customer contract.
- Label metrics with operation IDs, request hashes, queries, URLs, subjects, or error details: rejected because these create unsafe cardinality and disclosure risks.
- Install a vendor exporter before a staging control plane exists: rejected because it would invent an integration and secret lifecycle without deployment authority.
