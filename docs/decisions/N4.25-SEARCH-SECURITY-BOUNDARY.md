# N4.25: Search browser, retrieval, cache, and prompt-injection boundary

- **Status:** accepted; repository-verified, runtime/staging proof unavailable
- **Date:** 2026-07-31
- **Ticket:** N4.25

## Decision

Use a browserless control plane plus a disposable Crawl4AI execution plane. The browser worker has no public or cluster Service and no direct Internet egress. It can talk only to an internal retrieval-authorization gateway whose per-request decisions reuse Clervo URL/protocol, DNS/address, redirect, MIME, byte, robots, deadline, and cancellation controls. Exact runtime attestation is part of health, not an operator assertion. Missing/invalid attestation, an engaged kill switch, or unresolved orphans prevents `ready`.

The cache stores only current-page evidence material under `normalized URL + exact route identity + request-policy hash`. It does not store customer identity/query payload, secrets, wallet material, cookies, headers, browser profiles, or session state. Environment namespace, body hash, record hash, fetched/expiry timestamps, and route/policy identity are verified on read. Stale material is returned only for an explicitly degraded upstream, within a bound, and with `stale_while_degraded` disclosure.

Retrieved content remains exact, attributed untrusted evidence. A hash-bound boundary gives it zero ability to alter routing, tools, payments, system policy, citation construction, or execution. Content is retained for evidence/citation; it is never interpreted as policy.

## Rejected alternatives

1. Public or internal raw Crawl4AI HTTP API: rejected because it creates a browser/action surface and caller-controlled configuration.
2. Direct browser egress plus post-hoc transcript review: rejected because review after connection cannot prevent SSRF or DNS rebinding.
3. Kubernetes IP allowlists for arbitrary sites: rejected because dynamic page assets require per-request hostname/DNS/socket authorization; the browser instead gets gateway-only egress.
4. Persistent browser pools/profiles: rejected because cookies, service workers, storage, downloads, and cross-job state can leak.
5. Process-local or query-keyed search cache: rejected because it is neither durable nor safely bound to source route/policy identity.
6. Silent stale fallback: rejected because freshness and degraded reuse must be visible.
7. Regex removal of prompt-like text: rejected because it damages exact evidence and still cannot establish authority separation.

## Consequences and limitations

The gateway becomes a security-critical component and must itself be independently isolated, authenticated, observed, and staging-tested. Standard Kubernetes NetworkPolicy cannot express arbitrary dynamic FQDN policy, so its only job here is to confine the browser to the gateway. Infrastructure limits and adapter receipts are both required; neither substitutes for the other.

No browser/container runtime exists in this execution environment, and the staging identity is absent. The Deployment therefore deliberately has zero replicas, an invalid image placeholder, `imagePullPolicy: Never`, and an engaged kill switch. This is honest fail-closed production configuration, not a live browser claim. A later authorized staging step must supply a digest-pinned image/gateway and collect real runtime/network/cleanup evidence before readiness.
